OpenCode: aprende a trabajar con agentes de IA

Qué es un modelo de lenguaje, qué es un agente y cómo usar OpenCode, el agente de código abierto que corre en tu terminal. Cada sección termina con un bloque de fuentes verificables y videos en español con su autoría.

1. Fundamentos de LLMs

1.1 ¿Qué es un LLM? ¿Cómo funciona?

Un LLM (large language model, modelo de lenguaje grande) es un modelo de aprendizaje automático entrenado con enormes cantidades de texto. Su tarea básica es predecir la siguiente pieza de texto (token) dado lo que ya vio; al repetir esa predicción, genera respuestas completas.

El mecanismo central es el transformador y su mecanismo de atención: el modelo pondera qué palabras del contexto son relevantes para predecir la siguiente. No «piensa» ni «entiende» como una persona: reconoce patrones estadísticos aprendidos durante el entrenamiento. Después del entrenamiento inicial, se ajusta con instrucciones y retroalimentación humana para seguir indicaciones de forma útil.

  • Entrada y salida: texto (o tokens de texto).
  • Base: red neuronal de tipo transformador.
  • Ajuste: entrenamiento + alineación con instrucciones.

1.2 ¿Qué es un agente? Agente vs LLM

El LLM es el motor de texto: recibe un prompt y devuelve texto. Un agente es ese LLM más herramientas y un bucle de trabajo: puede leer y escribir archivos, ejecutar comandos, consultar la web y decidir qué hacer con el resultado.

La diferencia práctica, en un ciclo simple:

  • LLM solo: contesta preguntas con su conocimiento estático.
  • Agente: observa tu proyecto, ejecuta acciones (editar, probar, buscar) y ajusta su plan según lo que encuentra.

OpenCode es un agente: usa uno o varios LLMs como cerebro y les añade acceso al sistema de archivos, terminal, navegador y herramientas de desarrollo. El patrón «LLM + herramientas + bucle» está documentado en la guía de Anthropic sobre agentes efectivos y en el curso de agentes de Hugging Face.

1.3 ¿Cómo se mide la inteligencia de un LLM? Qué mirar para elegir modelo

No existe una única medida. Se combinan benchmarks y criterios prácticos:

  • LMArena: votación humana comparando respuestas de dos modelos a ciegas. Mide preferencia percibida, no exactitud.
  • Artificial Analysis: comparativas independientes de calidad, velocidad (tokens por segundo) y precio por millón de tokens.
  • SWE-bench: resuelve issues reales de repositorios de software; muy relevante si vas a usar el modelo para programar.
  • Open LLM Leaderboard (Hugging Face): tablas de benchmarks abiertos para modelos, incluidos los abiertos.

Para elegir modelo en un agente como OpenCode, mira:

  • Calidad en tareas de código (SWE-bench) y conversación.
  • Velocidad: tokens por segundo; afecta el tiempo de cada iteración.
  • Ventana de contexto: cuánto código/prompt cabe.
  • Costo: precio por millón de tokens de entrada y salida.
  • Disponibilidad en tu proveedor (OpenCode permite varios).

1.4 ¿Cómo funciona el conteo de tokens?

Los modelos no leen caracteres: dividen el texto en tokens, unidades que pueden ser palabras completas, fragmentos de palabra o signos. Como regla general, un token equivale a unas 4 letras en inglés (menos en español por su morfología) y a menos de una palabra promedio.

El tokenizador es la pieza que hace esa división, y es específico de cada modelo. El conteo importa por tres motivos:

  • Contexto: la ventana del modelo se mide en tokens (entrada + salida).
  • Costo: los proveedores cobran por token procesado.
  • Rendimiento: a más tokens, más lenta y cara cada llamada.

Puedes probar la división en el tokenizador interactivo de OpenAI, y el curso de midudev explica el concepto con ejemplos para desarrolladores.

2. OpenCode

2.1 ¿Qué es? vs ClaudeCode | Cursor | Codex

OpenCode es un agente de IA de código abierto que se usa desde la terminal: una interfaz de texto (TUI) donde le describes una tarea y el agente edita archivos, ejecuta comandos y propone cambios. Es multi-proveedor: funciona con Anthropic, OpenAI, Google, modelos locales y el servicio gratuito OpenCode Zen.

Comparación objetiva con las alternativas más conocidas:

Comparativa: OpenCode vs Claude Code vs Cursor vs Codex
Criterio OpenCode Claude Code Cursor Codex
Tipo Agente de terminal (TUI), open source Agente de terminal, propietario Editor/IDE con IA integrada Agente de terminal + integración en GitHub
Código abierto Sí No No No
Proveedores de modelo Multi: Anthropic, OpenAI, Google, Zen, locales Anthropic (Claude) Multi (trae modelos propios + trae el tuyo) OpenAI
Configuración opencode.json + AGENTS.md settings.json + CLAUDE.md Interfaz gráfica + reglas por proyecto Config por CLI + reglas
Modelos gratuitos Sí, vía OpenCode Zen No (suscripción o API) Prueba limitada Cuota en planes

2.2 OpenCode Zen: cuenta y modelos gratuitos

OpenCode Zen es el servicio de modelos de OpenCode: creas una cuenta gratuita y obtienes acceso a modelos de varios proveedores con una cuota gratuita, sin tarjeta de crédito. Es la vía más rápida para probar OpenCode sin configurar claves de API.

i

Zen gratis = sin tarjeta. La cuenta gratuita no requiere método de pago.

La documentación oficial explica los límites de la cuota gratuita, los modelos disponibles y cómo escalar a planes de pago si los necesitas.

2.3 Conectar modelos Zen a OpenCode

Dentro de la interfaz de OpenCode, el comando /connect abre el asistente de conexión: eliges proveedor, autorizas con tu cuenta y seleccionas modelo. Para Zen, el flujo es:

terminal
# 1. Instala OpenCode y ejecútalo en tu proyecto
$ opencode

# 2. Dentro de la interfaz, escribe:
/connect

# 3. Elige "OpenCode Zen" → se abre el navegador para iniciar sesión
# 4. Vuelve a la terminal y selecciona un modelo de la lista
# Listo: el modelo Zen queda conectado sin claves de API manuales

2.4 Multi-proveedor

OpenCode no está atado a un solo proveedor. Puedes usar varios a la vez y elegir cuál responde cada tarea:

  • Zen: modelos gratuitos con cuenta.
  • Anthropic / OpenAI / Google: tus claves de API, con opencode auth login.
  • Modelos locales: Ollama y otros servidores locales.
  • Proveedores compatibles: la lista completa está en la documentación de providers y models.

La selección de modelo por defecto y por tarea se configura en opencode.json (sección 3.3).

3. Estructura .opencode/

3.1 Carpetas y uso

La carpeta .opencode/ concentra la configuración del proyecto para OpenCode. Este mismo repositorio es el ejemplo vivo: su estructura es la siguiente.

estructura (este repo)
.opencode/
├── agents/     # definiciones de agentes personalizados (orchestrator, frontend-dev, …)
├── commands/   # comandos personalizados de la interfaz
├── docs/       # documentación interna vinculante (trinity, perf, sync)
├── plugins/    # plugins JS: hooks y lógica de arranque (bootstrap, env-protection, …)
├── prompts/    # plantillas de prompt por agente (agent-knowledge-awareness.md, …)
├── secrets/    # claves locales (ignoradas por git)
└── skills/     # habilidades reutilizables (accessibility-wcag, seo, playwright, …)
  • agents/ — archivos Markdown que definen el rol de cada agente: responsabilidades, reglas y límites. En este repo hay cuatro: orchestrator, frontend-dev, code-review y release-manager.
  • skills/ — habilidades (instrucciones) que se cargan bajo demanda, por ejemplo accessibility-wcag, seo o playwright-best-practices.
  • commands/ — comandos personalizados disponibles dentro de la interfaz de OpenCode.
  • docs/ — documentación interna de referencia: aquí vive trinity-architecture.md, performance-reliability.md y directive-sync.md, que regulan cómo se escribe código en el proyecto.
  • prompts/ — plantillas de prompt que los agentes usan como base, referenciadas desde opencode.json con {file:…}.
  • plugins/ — código JavaScript que se ejecuta como plugin (por ejemplo, proteger variables de entorno o cargar reglas).
  • secrets/ — claves y tokens locales; está en .gitignore y nunca se sube al repositorio.

3.2 vs ClaudeCode (estructura/config)

3.3 opencode.json: qué es y por qué importa

opencode.json es el archivo de configuración central de OpenCode en un proyecto: define qué instrucciones leer, qué permisos tiene el agente, qué agentes existen, qué plugins y servidores MCP se cargan y cuál es el agente por defecto.

Un extracto real de este repositorio:

opencode.json (este repo)
{
  "$schema": "https://opencode.ai/config.json",
  "instructions": [".opencode/docs/skills-settings-rules.md"],
  "permission": {
    "bash": {
      "*": "ask",
      "git *": "allow",
      "pnpm *": "allow",
      "rm *": "deny",
      "grep *": "allow"
    }
  },
  "default_agent": "orchestrator",
  "tools": { "playwright*": false }
}
!

No se edita sin aprobación. En este proyecto, opencode.json es un contrato (SPEC.md §4): los cambios los decide el orquestador con aprobación del usuario, porque de ahí salen permisos y agentes.

Por qué importa: permisos (qué puede ejecutar el agente), agentes (quién hace cada tarea) y herramientas (qué está activo) se deciden aquí, no en el prompt de cada conversación.

4. Trabajar con agentes

4.1 Agente. Plan vs Build

Un agente de OpenCode trabaja en dos modos principales. En modo Plan propone un plan y no toca archivos: lees, corriges y apruebas. En modo Build ejecuta: edita, crea y prueba. La tecla Tab alterna entre modos dentro de la interfaz.

Por qué importa: el modo Plan convierte al agente en un compañero de diseño (revisa antes de actuar), y el modo Build en un ejecutor. Alternar entre ambos evita que el agente haga cambios grandes sin que tú veas el rumbo.

4.2 Loop prompt → crear → iterar (y por qué importa)

El flujo real de trabajo con un agente es un bucle:

  1. Prompt: describes la tarea con contexto (qué, para quién, restricciones).
  2. Crear: el agente propone o ejecuta cambios.
  3. Iterar: revisas el resultado, corriges el rumbo y repites hasta que esté bien.

Por qué importa: la calidad no sale del primer prompt, sale de iterar con criterio. El «vibe coding» (aceptar la primera respuesta sin revisar) produce software frágil; el método de especificar, revisar e iterar produce software robusto. La documentación de OpenCode describe el ciclo plan → iterate → build → undo como la forma prevista de trabajar.

4.3 Permisos (y por qué importan)

El agente ejecuta comandos reales en tu máquina. Los permisos definen qué puede hacer sin preguntar (allow), qué debe consultar (ask) y qué tiene prohibido (deny). El bloque de permisos de este repositorio:

opencode.json → permission (este repo)
"permission": {
  "bash": {
    "*": "ask",        // todo comando desconocido pregunta antes
    "git *": "allow",  // git no pregunta
    "pnpm *": "allow", // pnpm no pregunta
    "rm *": "deny",    // rm está prohibido
    "grep *": "allow"  // búsquedas sin pregunta
  }
}
i

Por qué importan: "*": "ask" significa que cualquier comando fuera de la lista blanca requiere tu aprobación. Es el límite de daño: un error del agente no puede borrar archivos (rm denegado) ni ejecutar nada raro sin que tú lo veas.

4.4 SPEC.md / AGENTS.md / DESIGN.md (y por qué importan)

Los agentes trabajan mejor cuando el proyecto les dice qué hacer. Tres archivos de raíz cumplen ese rol en este repositorio:

  • SPEC.md — qué construir: contenido, estructura, fuentes y criterios de aceptación.
  • DESIGN.md — cómo se ve: paleta, tipografía, espaciado, motion y tokens de diseño vinculantes.
  • AGENTS.md — cómo se trabaja: stack, estructura, reglas por rol, flujo git y permisos de cada agente.

Un extracto real de AGENTS.md:

AGENTS.md (este repo)
# Agent Context
Goal: **Educational docs site** — what OpenCode is, how to work with it.
Web content 100% Spanish. Project files 100% English.
Deploy: **GitHub Pages** (`gh-pages`).

## Tech Stack
Bund: Vite | Struct: HTML5 | Style: Native CSS (lightningcss) |
Logic: JS (ES6+)  PM: **pnpm only**

## Dev Rules by Owner
| Area      | Owner           | File                               |
| --------- | --------------- | ---------------------------------- |
| HTML+CSS+JS | @frontend-dev | .opencode/agents/frontend-dev.md |
| Audit     | @code-review    | .opencode/agents/code-review.md    |

## Git Flow
**main**=prod. Merge from `release/*`/`hotfix/*` only.
**develop**=daily integ. All merges via PR.

Por qué importan: sin especificación, el agente improvisa. Con SPEC, DESIGN y AGENTS, cada agente sabe qué construir, con qué estética y bajo qué reglas — y el revisor (@code-review) puede rechazar lo que no cumpla. El método de «software definido por especificaciones» lo popularizó MoureDev en su proyecto hello-sdd.

4.5 Agentes personalizados: primary vs sub-agent

OpenCode permite definir agentes propios en opencode.json. Hay dos modos:

  • Primary: aparece en el selector de agentes de la interfaz; coordina el trabajo, delega y ve la conversación principal. En este repo, orchestrator.
  • Sub-agente: se ejecuta como tarea dentro de otra sesión; tiene herramientas limitadas y devuelve un resultado. En este repo, frontend-dev, code-review y release-manager.

Definiciones reales de este repositorio:

opencode.json → agent (este repo)
"agent": {
  "orchestrator": {
    "description": "Main orchestrator. Brainstorms, maps architectural
      blueprints, and executes the sequential development pipeline.",
    "mode": "primary",
    "tools": { "task": true, "read": true },
    "prompt": "{file:.opencode/prompts/agent-knowledge-awareness.md}"
  },
  "frontend-dev": {
    "description": "Consolidated developer sub-agent. Builds cohesive
      features writing HTML structures, modular styles, and JS
      interaction in tandem.",
    "mode": "subagent",
    "tools": { "write": true, "edit": true, "read": true, "task": true },
    "prompt": "{file:.opencode/prompts/agent-knowledge-awareness.md}"
  }
}

Cada agente tiene una descripción (para que el modelo sepa cuándo usarlo), un modo, un conjunto de herramientas y un prompt opcional desde .opencode/prompts/. El detalle del rol vive en .opencode/agents/*.md.

4.6 Skills (vs Claude Code)

Una skill es un conjunto de instrucciones reutilizables que el agente carga bajo demanda cuando la tarea coincide con su descripción: por ejemplo, accessibility-wcag, seo o frontend-design en este repositorio. En lugar de repetir reglas en cada prompt, el agente «abre» la skill cuando la necesita.

vs Claude Code: ambos soportan skills de proyecto; Claude Code las llama agent skills y las guarda en .claude/skills/. OpenCode mantiene un registro abierto en skills.sh con skills compartidas por la comunidad.

El curso de midudev introduce el concepto de skills con ejemplos prácticos.

4.7 Prompts (vs Claude Code)

Los prompts en OpenCode son plantillas de instrucción asociadas a un agente, referenciadas desde opencode.json con la sintaxis {file:ruta}. En este repo, todos los agentes usan .opencode/prompts/agent-knowledge-awareness.md: un prompt que les recuerda leer las reglas del proyecto antes de actuar.

vs Claude Code: la función equivalente son los slash commands: comandos personalizados (a menudo prompts) que se invocan con / dentro de la interfaz. En OpenCode, los comandos personalizados viven en .opencode/commands/.

4.8 Plugins (vs Claude Code)

Los plugins de OpenCode son código JavaScript que extiende el comportamiento del agente: hooks que se ejecutan en momentos del ciclo de vida (arranque, cada mensaje, etc.). En este repo hay cuatro plugins activos: bootstrap.js, env-protection.js, load-rules.js y ponytail-mode.js, declarados en opencode.json con "plugin": ["@dietrichgebert/ponytail"] y archivos locales.

vs Claude Code: la función equivalente son los hooks (preToolUse, PostToolUse, etc.) definidos en settings.json. Ambos permiten automatizar reglas y protecciones, con enfoques distintos: plugins JS en OpenCode, hooks configurables en Claude Code.

4.9 MCP (vs Claude Code)

MCP (Model Context Protocol) es un estándar abierto para conectar herramientas externas a agentes: servidores locales o remotos que exponen recursos y funciones. En este repo hay tres servidores MCP configurados en opencode.json: playwright-test (probar la interfaz), codegraph (índice del código) y context7 (documentación de librerías).

vs Claude Code: Claude Code también soporta MCP y usa el mismo protocolo; la diferencia está en la configuración (en opencode.json vs settings.json / .mcp.json). El protocolo en sí es compartido: aprenderlo sirve para ambos.

5. Ejemplo real: este proyecto

5.1 El proyecto

Este sitio es el ejemplo vivo de todo lo explicado: está construido con Vite + HTML5 + CSS nativo + JS ES6, gestionado con pnpm y desplegado en GitHub Pages. El repositorio implementa, de verdad, la estructura .opencode/, el opencode.json y los agentes descritos arriba.

El ciclo de desarrollo y despliegue, en comandos reales:

terminal
# Instalar dependencias (pnpm, no npm)
pnpm install

# Desarrollo local con recarga en caliente
pnpm run dev

# Build de producción (Vite → dist/, con base /opencode-tutorial/)
pnpm run build

# Desplegar: build + publicar la carpeta dist/ en la rama gh-pages
pnpm deploy

El flujo completo del proyecto está documentado en AGENTS.md: rama main = producción, develop = integración diaria, ramas feature/* para trabajo nuevo, release/* para publicar y hotfix/* para correcciones urgentes.

5.2 Flujo de trabajo

Así trabaja este repositorio con sus agentes personalizados:

  1. @orchestrator (agente primary) planifica, delega y decide merge/release, con checkpoint del usuario antes de publicar.
  2. @frontend-dev (sub-agente) escribe HTML, CSS y JS en ramas feature/*, sujeto a los contratos de arquitectura y rendimiento.
  3. @code-review (sub-agente) audita el código contra SPEC, DESIGN y los checklists; sin su STATUS: APPROVED no hay merge.
  4. @release-manager (sub-agente) crea ramas de release, merge a main, tag + GitHub Release y despliegue con pnpm deploy → rama gh-pages → sitio en vivo.

Reglas del proyecto en AGENTS.md, contenido y fuentes en SPEC.md, diseño vinculante en DESIGN.md, y la configuración de todo (permisos, agentes, MCP, plugins) en opencode.json. Ese es el punto: no es teoría, es cómo funciona este sitio.
